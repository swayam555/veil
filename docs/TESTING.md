### Detection accuracy

`DetectionEvalTest` scans 510 prompts generated by `detection-core/src/test/resources/eval/generate.py` (seeded): realistic
support, KYC, finance and engineering prompts with planted values, plus decoys (12-digit order numbers that fail Verhoeff,
16-digit tracking numbers that fail Luhn, UUIDs, git SHAs, version strings, timestamps). It fails the build below 0.95
precision / 0.90 recall per pattern detector (0.90 / 0.85 for names) and writes `detection-core/target/detection-eval.md`.

Last run: all 15 span types at precision and recall 1.000, 0 mistakes, average scan time 0.24 ms (0.4 ms on earlier
runs). The first run had one mistake: a 14-digit Luhn-valid number next to "account number" was read as a card (card
precision 0.982). Fixed with "penalty" context words. Because the set
is synthetic, these scores overstate real-world accuracy, especially for names.

## Load (k6, `scripts/load-test.sh`)

Every prompt is unique (random names, numbers and subjects) and sent with `Cache-Control: no-cache`, so neither the
embedding cache nor the semantic cache flatters the numbers. "Scan" is the Scan API (pure Veil cost: auth, limits,
detection including embeddings, audit); "chat" adds the simulated provider's 250–600 ms.

| Offered load | Scan p95 | Errors | Notes |
|---|---|---|---|
| 40 scan + 20 chat req/s | 25.8 ms | 0% | |
| 70 scan + 20 chat req/s | 24.2 ms | 0% | |
| 90 scan + 30 chat req/s | 44.6 ms | 0% | |
| 110 scan + 40 chat req/s, first version | 2.0 s | 46% | embeddings contending for cores; timeouts |
| 110 + 40, with dynamic batching + shedding, fail-closed | 860 ms | 16% (fast 503 `Retry-After`) | 84% fully checked |
| 110 + 40, with dynamic batching + shedding, fail-open | 773 ms | 0% | excess checked with patterns only |

On the host (outside the Docker VM) one embedding takes 4–6 ms and batching reaches ~335–430 texts/s; the Docker Desktop
VM is roughly 3× slower, so a real Linux server would sustain more per node.

## Bugs found by testing (and fixed)

| Found by | Bug | Fix |
|---|---|---|
| Accuracy eval | A 14-digit Luhn-valid account number was reported as a card | Context words that point to another kind of number lower card confidence |
| Unit test | `Bearer eyJ…` was reported as a generic credential, hiding the JWT | The generic secret detector skips JWT-shaped values |
| Unit test | "Apache Kafka" read as a person ("with" counted as name context) | Generic prepositions removed from name context |
| Semantic tests | Paraphrased injections and health topics missed; generic questions about earnings flagged | More examples, thresholds re-tuned to similarity ≥ 0.42 and margin ≥ 0.15 over neutral |
| Integration test | The semantic cache never hit: with RESP3, `FT.SEARCH` replies are maps | A dedicated RESP2 connection for vector search |
| Integration test | Config and key events never arrived: custom consumer factories ignored the resolved bootstrap servers | Build them from Boot's consumer factory |
| Integration test | Testcontainers' Kafka 3.9 refused `0.0.0.0` as an advertised address on Docker Desktop | Kafka 3.8.1 for tests, `TESTCONTAINERS_HOST_OVERRIDE=localhost` |
| Browser test | Shadow AI returned 500 (ORDER BY on column aliases) | Order by the aggregate |
| Browser test | Topic-only incidents (no fingerprints) failed to fold and went to the dead-letter topic | `coalesce` to an empty array |
| Browser test | Flagged pastes created an incident each, burying real ones | Incidents only for blocked, critical, injection and masked output |
| Browser test | Simulator prompts repeated too much (72% cache hits) | Varied subjects and audiences |
| Browser test | Native `confirm()` dialogs block the page (and automation) | In-app confirmation dialog |
| Smoke test | `Cache-Control: no-cache` also stopped the answer being cached | It only skips the lookup |
| Load test | 46% of requests failed at 140 req/s: every ONNX inference used every core | Own ONNX session, dynamic batching, single-digit threads per inference |
| Load test | Overload made every queued request time out together | Load shedding on in-flight detections, decided by fail mode |
| Chaos test | With Redis restarted and the control plane down, known keys were refused, taking every app down | Stale-if-error key cache (revocations still evict) |
| Review for k8s | Two control-plane replicas could both seed the demo org | Postgres advisory lock around seeding |
| Screenshot review | An incident blocked for a non-data reason (model allowlist) got the title "blocked for …" | Title from the policy's reason |
| Mobile viewport (Playwright, 390 px) | Policies page overflowed by 55 px: grid columns sized to the rules table | `grid-cols-1` (minmax(0, 1fr)) on every two-column screen |
| Final re-run of the chaos test | "Audit events buffered" sometimes read 0 just after Kafka went down: the Kafka client holds unsent records itself until its delivery timeout, so only failed sends reached our buffer | The gauge now counts our retry buffer plus sends still in flight |

## Manual test script (about 15 minutes)

Start the stack (`docker compose up --build`), open http://localhost:3004.

1. **Landing page.** The hero animation types a prompt, highlights four values, turns them into placeholders, shows the
   model's answer with placeholders, then the restored answer. Scroll: problem stats with sources, how it works, adoption
   paths, architecture.
2. **Sign in** with "Asha Rao" (admin). You land on the Overview. Press **Start simulated traffic**. Within a minute the
   live feed fills, the chart grows, and findings appear by type and team.
3. **Playground.** Click **Customer reply**: four values are highlighted teal as you look (decision "Redacted"). **Send
   through Veil**. Card 2 shows `[PERSON_1]`, `[EMAIL_1]`…; card 4 shows the real name back. The timing bar shows detection
   in milliseconds next to the model's hundreds.
   - **Leaked AWS key** → red "Nothing was sent to the model".
   - **Unreleased results** with team Finance → "Sent to the on-premises model".
   - **Prompt injection** → blocked.
4. **Activity.** Filter by decision "Blocked". Open a row: the prompt is stored redacted, findings have fingerprints, no values.
5. **Incidents.** Open the critical "API key or token blocked" incident (it counts occurrences). **Explain this incident**,
   then **Resolve**.
6. **Policies.** In the copilot type "Block IBAN numbers for the Sales team", **Draft rules**, **Add 1 rule(s) to the
   draft**, **Publish**. In Dry run, choose Sales, paste `Refund to IBAN GB82 WEST 1234 5698 7654 32`, **Run**: Blocked.
   Restore the previous version from History.
7. **Keys & teams.** **New key** → copy it (shown once). Use it with curl (Integrations has the snippet). **Revoke**: the
   in-app dialog asks; within a couple of seconds the key gets 401.
8. **Providers.** Set "Veil Echo (simulated cloud model)" to **Outage**, send a gpt-4o-mini prompt from the Playground:
   "veil-echo: HTTP 503 (simulated outage)" then served by the EU backup. Keep sending: the circuit shows Open. Set it back
   to Healthy.
9. **Extension.** Integrations → **Download extension**, unzip, `chrome://extensions` → Developer mode → Load unpacked.
   Options: server `http://localhost:3004`, key `vk_ext_demo_support_B6wE3nU8yT1qA5zR`, your email → Save and test
   ("Connected to Acme Fintech Pvt Ltd as team Support"). Open http://localhost:3004/demo/chat and paste
   `Customer Priya Sharma, Aadhaar 2345 6789 0124, wants a refund`: the overlay offers **Paste redacted**. Type a message
   with `AKIAIOSFODNN7EXAMPLE` and press Enter: blocked, no "send anyway". Shadow AI now shows the site.
10. **Read-only role.** Sign out, sign in as "Vikram Shah" (auditor): everything is visible, but publish, revoke and incident
    status buttons are gone, and the API refuses changes (403).
11. **Compliance.** Detected vs protected per regulation, and the controls list. Activity → **Export CSV** downloads the log.
